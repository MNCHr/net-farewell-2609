# 퇴임 선물 참여 조사 사이트 — 설계

- 작성일: 2026-08-12
- 상태: 승인됨 (구현 계획 작성 대기)

## 1. 목적

같은 본부의 책임 2인이 퇴직한다. 퇴임 선물에 참여할 사람을 모아야 한다.

메일로 조사하면 두 퇴직자 모두와 친분이 있지는 않은 사람을 배려하기 위한 안내가 길어지고,
회신이 자유 서술로 쏟아져 취합이 지저분해진다.
대신 **각자 조용히 체크만 하면 되는 웹 페이지**를 만든다.

핵심 배려: **"두 분 중 한 분만" 또는 "둘 다 참여 안 함"을 눈치 보지 않고 고를 수 있어야 한다.**
따라서 두 사람을 각각 독립된 체크박스로 두고, 아무것도 체크하지 않은 제출도 정상 응답으로 받는다.

### 성공 기준

- 사내망 PC 브라우저에서 접속되고 제출이 저장된다
- 참여자는 30초 안에 끝낼 수 있다
- 참여자는 남의 응답을 볼 수 없다
- 관리자는 집계와 개별 응답을 보고, 비밀번호를 초기화하고, 대리 입력할 수 있다
- 응답자가 나중에 마음을 바꾸면 스스로 수정할 수 있다

### 제약

- 사내망에서 `github.io`와 `script.google.com`은 열린다 (확인됨)
- 그 외 도메인은 미확인. Firebase 등은 전제하지 않는다
- 대상 인원 약 108명
- 금액은 참여자 수 확정 후 n분의 1. 사이트는 금액을 다루지 않는다

### 범위 밖 (명시적으로 하지 않는 것)

- 마감 기한 자동 잠금
- 참여 현황의 참여자 공개
- 소속 팀/부서, 롤링페이퍼 메시지, 연락처 수집
- 금액 계산, 입금 확인, 정산
- 사전 등록 명단 및 미응답자 추적 (자유 입력 방식을 택했으므로 원리적으로 불가)

## 2. 아키텍처

정적 사이트가 화면을 담당하고, Apps Script가 API 서버, 구글시트가 DB 역할을 한다.

```
[사내망 PC 브라우저]
      │  ① 정적 파일 (HTML/CSS/JS)
      ▼
[GitHub Pages]  <owner>.github.io/<repo>/
      │  ② POST /exec  (JSON in text/plain)
      ▼
[Apps Script Web App]   실행: 소유자 / 액세스: 모든 사용자
      │  ③ SpreadsheetApp
      ▼
[Google Sheet]  소유자 개인 드라이브, 비공개
```

### 신뢰 경계

**브라우저는 아무것도 신뢰받지 않는다.** 다음은 전부 Apps Script 안에서만 판정한다.

- 비밀번호 검증
- 관리자 권한 검증
- 사번/이름 정규화의 최종 판정
- 통계 계산

브라우저가 하는 정규화·검증은 **사용자 편의를 위한 미리보기일 뿐**이며, 서버는 클라이언트가 보낸 값을 다시 정규화하고 다시 검증한다.

### 계정

구글시트와 Apps Script는 **개인 gmail 계정**으로 만든다.
회사 워크스페이스 계정은 웹앱 배포 시 「액세스: 모든 사용자」 옵션이 정책으로 차단된 경우가 많고,
행사 종료 후 데이터를 통째로 삭제하기도 개인 계정이 깔끔하다.

### 파일 구성

```
etri-network-farewell-2609/
├── index.html            참여자 화면 (단일 페이지, 단계 전환은 JS)
├── admin.html            관리자 화면 (어디에도 링크되지 않음)
├── test.html             연결 진단 페이지 (0단계 전용)
├── tests.html            순수 로직 단위 테스트 러너
├── robots.txt            전체 크롤링 차단
├── assets/
│   ├── config.js         퇴직자 표기명 · /exec 주소  ← 운영 시 여기만 수정
│   ├── normalize.js      사번/이름 정규화 (순수 함수, 테스트 대상)
│   ├── api.js            통신 계층 (전송 방식 전환 · 에러 · 재시도)
│   ├── app.js            참여자 화면 로직
│   ├── admin.js          관리자 화면 로직
│   └── style.css
├── apps-script/
│   └── Code.gs           서버 코드 원본 (git 버전관리 → 편집기에 붙여넣기)
└── README.md             배포 순서
```

`apps-script/Code.gs`를 저장소에 두는 이유: Apps Script 편집기에는 되돌리기 안전망이 약하다.
원본이 git에 있으면 언제든 복구된다. 편집기와 저장소 중 **저장소가 정본**이다.

## 3. 데이터 모델

### 시트 `responses`

관리자가 시트를 직접 열었을 때 읽히도록, 사람이 보는 값을 앞쪽에 둔다.

| 열 | 이름 | 타입 | 설명 |
|---|---|---|---|
| A | `empNo` | 텍스트 | 정규화된 사번 5자리. **셀 서식을 텍스트로 지정** (앞자리 0 보존) |
| B | `name` | 텍스트 | 정규화된 이름 |
| C | `pickA` | 불리언 | 퇴직자 A 참여 여부 |
| D | `pickB` | 불리언 | 퇴직자 B 참여 여부 |
| E | `pwHash` | 텍스트 | Base64. **빈 문자열이면 비밀번호 미설정** (관리자 대리 입력 행) |
| F | `salt` | 텍스트 | 레코드별 랜덤 16바이트 Base64 |
| G | `createdAt` | ISO 문자열 | 최초 생성 시각 |
| H | `updatedAt` | ISO 문자열 | 최종 수정 시각 |
| I | `updatedBy` | 텍스트 | `self` \| `admin` |
| J | `status` | 텍스트 | `active` \| `deleted` |
| K | `failCount` | 정수 | 비밀번호 연속 실패 횟수 |
| L | `lockedUntil` | ISO 문자열 \| 빈칸 | 잠금 해제 시각 |

`empNo`가 사실상의 기본키다. `status='deleted'` 행도 남아 있으므로,
조회는 항상 `empNo`가 같고 `status='active'`인 행을 찾는다.
삭제된 사번으로 다시 가입하면 새 행을 만들지 않고 기존 행을 `active`로 되살린다
(같은 `empNo`의 `active` 행이 둘 이상 생기는 것을 원천 차단한다).

### 시트 `log`

| 열 | 이름 | 설명 |
|---|---|---|
| A | `at` | ISO 시각 |
| B | `action` | `create` / `update` / `admin_reset_pw` / `admin_upsert` / `admin_delete` |
| C | `empNo` | 대상 사번 |
| D | `actor` | `self` \| `admin` |
| E | `detail` | 변경 요약 (비밀번호 원문·해시는 절대 기록하지 않음) |

관리자 조작을 나중에 되짚기 위한 감사 기록이다.

### Script Properties (시트가 아님)

| 키 | 값 |
|---|---|
| `ADMIN_PW_HASH` | 관리자 비밀번호 SHA-256 해시 (Base64) |
| `ADMIN_SALT` | 관리자용 솔트 |
| `ADMIN_FAIL_COUNT` | 관리자 로그인 연속 실패 횟수 |
| `ADMIN_LOCKED_UNTIL` | 관리자 잠금 해제 시각 |

시트에 두지 않는 이유: 시트를 실수로 공유해도 관리자 권한은 넘어가지 않아야 한다.

### 퇴직자 두 분의 표기

`assets/config.js`에 하드코딩한다.

```js
export const RETIREE_A = { key: 'A', label: '김OO 책임님' };
export const RETIREE_B = { key: 'B', label: '이OO 책임님' };
```

서버 왕복을 하나 줄이고, 표기를 고칠 일이 생겨도 `git push` 한 번이면 된다.
표기를 `김OO` 형태로 두는 것은 의도된 것이다 (6.3 참조).

## 4. 정규화 규칙

**이 문서가 정규화 규칙의 정본이다.** 같은 규칙을 `assets/normalize.js`(브라우저)와
`Code.gs`(서버)에 각각 구현한다. 두 구현은 동일한 테스트 케이스 표를 공유한다 (9장).

### 사번

1. 숫자가 아닌 문자를 모두 제거한다 (공백, 하이픈, 전각 숫자는 반각으로 변환 후 처리)
2. 결과가 빈 문자열이면 → 오류 `BAD_EMPNO`
3. 길이가 5를 초과하면 → 오류 `BAD_EMPNO`
4. 길이가 5 미만이면 앞에 `0`을 채워 5자리로 만든다

`1234` → `01234`, `01234` → `01234`, `1 2 3 4` → `01234`, `123456` → 오류

**목적**: 사번이 `01234`인 사람이 앞의 0을 빼고 `1234`로 입력해도 같은 한 사람으로 모이게 한다.
이 실수는 실제로 가장 흔하다.

### 이름

1. 모든 공백 문자를 제거한다 (반각/전각 공백, 탭 포함)
2. 유니코드 NFC 정규화를 적용한다 (한글 자모 조합 형태 차이 흡수)
3. 결과가 빈 문자열이면 → 오류 `BAD_NAME`
4. 길이가 20자를 초과하면 → 오류 `BAD_NAME`

`홍 길동` → `홍길동`

### 비밀번호

- **숫자 4자리**. 그 외는 오류 `BAD_PW`
- 저장: `Base64(SHA-256(salt + pw))`. **원문은 어디에도 저장하지 않는다**
- 따라서 관리자도 남의 비밀번호 원문을 볼 수 없다. 분실 시엔 조회가 아니라 **초기화**다

## 5. API

전부 `POST /exec` 단일 엔드포인트. 요청 본문은 JSON이며 `Content-Type: text/plain;charset=utf-8`.
`action` 필드로 분기한다.

### 공통 응답

```jsonc
{ "ok": true,  "data": { /* ... */ } }
{ "ok": false, "error": "WRONG_PW", "message": "비밀번호가 일치하지 않습니다.", "remaining": 3 }
```

`message`는 서버가 만든 한국어 문구를 그대로 화면에 띄운다.
문구가 서버에 있으면 나중에 표현을 고칠 때 재배포 한 번으로 끝난다.

### 오류 코드

| 코드 | 의미 |
|---|---|
| `BAD_EMPNO` / `BAD_NAME` / `BAD_PW` | 입력 형식 오류 |
| `NAME_MISMATCH` | 사번은 있는데 이름이 다름 (오타 방어선) |
| `WRONG_PW` | 비밀번호 불일치. `remaining` 동봉 |
| `LOCKED` | 연속 실패로 잠김. `lockedUntil` 동봉 |
| `NOT_FOUND` | 관리자 조작 대상이 없음 |
| `ADMIN_DENIED` | 관리자 비밀번호 불일치 |
| `BUSY` | 락 획득 실패 (동시 쓰기 폭주) |
| `SERVER_ERROR` | 그 외. 상세는 로그에만 남기고 사용자에겐 일반 문구 |

### 잠금 규칙 (참여자·관리자 공통)

- 비밀번호 불일치 시 `failCount`를 1 증가시킨다
- `failCount`가 5에 도달하면 `lockedUntil = 현재 + 10분`으로 설정한다
- 잠금 중 요청은 비밀번호를 검사하지 않고 즉시 `LOCKED`를 돌려준다 (카운터도 올리지 않는다)
- `lockedUntil`이 지난 뒤 첫 요청에서 **`failCount`를 0으로, `lockedUntil`을 빈칸으로 되돌린 뒤** 정상 판정한다
- 비밀번호가 일치하면 언제나 `failCount`를 0으로 초기화한다

관리자 쪽 카운터는 시트가 아닌 Script Properties(`ADMIN_FAIL_COUNT`, `ADMIN_LOCKED_UNTIL`)에 둔다.

### `ping` — 진단 전용

요청: `{ action: "ping" }`. 인증 없이
`{ ok:true, data:{ pong:true, sheetOk:true, headerOk:true, at:"..." } }`를 돌려준다.
`sheetOk`는 시트 접근이 실제로 되는지, `headerOk`는 `responses` 1행이 정해진 헤더와
정확히 일치하는지 확인한 결과다. 둘 다 `responses`의 데이터 행은 읽지도 쓰지도 않는다.
`test.html`에서만 사용한다.

### 참여자용

#### `auth` — 로그인 및 상태 판정

요청: `{ action, empNo, name, pw }`

정규화 후 판정표:

| `empNo`의 active 행 | 이름 | 비밀번호 | 결과 |
|---|---|---|---|
| 없음 | — | — | `ok`, `mode: "new"` — 아직 저장하지 않는다 |
| 있음 | 불일치 | — | `NAME_MISMATCH` |
| 있음, `pwHash` 빈칸 | 일치 | — | `ok`, `mode: "claim"` — 관리자 대리 입력 행. 기존 선택 동봉 |
| 있음 | 일치 | 불일치 | `WRONG_PW`, `failCount` 증가 |
| 있음 | 일치 | 일치 | `ok`, `mode: "existing"`, 기존 선택 동봉. `failCount` 0으로 초기화 |
| 잠김 상태 | — | — | `LOCKED` |

응답: `{ ok:true, data:{ mode, empNo, name, picks:{ A:bool, B:bool }, updatedAt } }`

`mode:"new"`일 때 **레코드를 만들지 않는다.** 확인 화면에서 사용자가 취소할 수 있고,
그 경우 오타 사번이 시트에 남으면 안 되기 때문이다. 실제 생성은 `save`에서 일어난다.

#### `save` — 선택 저장

요청: `{ action, empNo, name, pw, pickA, pickB }`

`auth`와 동일한 판정을 **다시** 수행한다 (상태 없는 설계이므로 매 요청이 스스로 인증한다).
통과하면:

- 행이 없으면 → 생성. `salt` 생성, `pwHash` 저장, `createdAt`/`updatedAt` 기록
- 행이 있고 `pwHash`가 빈칸이면 → **지금 보낸 비밀번호를 그 사람의 비밀번호로 설정**하고 갱신
- 행이 있으면 → `pickA`/`pickB`/`updatedAt` 갱신, `updatedBy='self'`

응답: `{ ok:true, data:{ picks, updatedAt } }`

세 번째 경우가 관리자 대리 입력과 본인 수정을 잇는 다리다.
관리자가 전화를 받고 대신 넣어준 사람도, 나중에 본인이 들어와 그대로 이어받아 수정할 수 있다.

### 관리자용

모든 관리자 요청은 `adminPw`를 동봉하고, 서버는 **매 요청마다** 이를 재검증한다.
세션도 토큰도 두지 않는다 — 상태가 없으면 세션 탈취 문제도 없다.

관리자 비밀번호도 5회 연속 실패 시 10분 잠금을 적용한다
(카운터는 Script Properties에 둔다).

#### `adminData`

응답:

```jsonc
{
  "ok": true,
  "data": {
    "stats": {
      "total": 82,      // active 응답 수
      "a": 76, "b": 71, // 각 퇴직자별 참여자 수
      "both": 68, "onlyA": 8, "onlyB": 3, "none": 3
    },
    "rows": [
      { "empNo":"01234", "name":"홍길동", "pickA":true, "pickB":true,
        "updatedAt":"...", "updatedBy":"self", "hasPw":true }
    ],
    "warnings": [
      { "type":"SAME_NAME_DIFF_EMPNO", "name":"홍길동", "empNos":["01234","01243"] },
      { "type":"SAME_EMPNO_DIFF_NAME", "empNo":"00777", "names":["김철수","김철순"] }
    ]
  }
}
```

`rows`에 `pwHash`와 `salt`는 **절대 포함하지 않는다.** `hasPw` 불리언만 내려보낸다.

`warnings`는 자유 입력 방식의 대가로 생기는 오타를 관리자 눈에 먼저 띄게 하는 장치다.
`SAME_EMPNO_DIFF_NAME`은 `deleted` 행까지 포함해 비교해야 잡힌다.

#### `adminResetPw`

요청: `{ action, adminPw, empNo }` → 해당 행의 `pwHash`/`salt`/`failCount`/`lockedUntil`을 비운다.
그 사람은 다음 로그인 때 입력하는 비밀번호가 새 비밀번호로 설정된다 (`mode:"claim"` 경로와 동일).

#### `adminUpsert`

요청: `{ action, adminPw, empNo, name, pickA, pickB }`

행이 없으면 만들고, 있으면 갱신한다. `updatedBy='admin'`.
**신규 생성 시 `pwHash`는 빈칸으로 둔다** — 관리자는 남의 비밀번호를 정하지 않는다.

사이트를 못 쓰는 사람의 대리 입력과, 사번 오타로 잠긴 사람의 구제가 모두 이걸로 처리된다.

#### `adminDelete`

요청: `{ action, adminPw, empNo }` → `status='deleted'`. **행을 지우지 않는다.**
잘못 눌러도 시트에서 되돌릴 수 있고, `log` 시트에도 기록이 남는다.

## 6. 화면

### 6.1 참여자 (`index.html`)

한 페이지 안에서 단계만 전환한다.

**1단계 · 랜딩** — 누가 퇴직하는지, 왜 모으는지, 그리고 세 가지 안내:
「두 분 다 / 한 분만 / 참여 안 함 모두 괜찮습니다」,
「금액은 참여 인원 확정 후 n분의 1」,
「제출 후에도 언제든 수정 가능」.
첫 번째 문구가 이 사이트를 만드는 이유이므로 눈에 띄게 배치한다.

**2단계 · 로그인** — 사번 / 이름 / 비밀번호(숫자 4자리).
사번 입력 중 **실시간으로 정규화 결과를 보여준다**:

```
사번  [ 1234        ]
      └ 사번 01234 으로 조회합니다 ✓
        (5자리입니다. 앞의 0은 빼고 쓰셔도 됩니다)
```

비밀번호 칸 아래: 「나중에 수정할 때 필요합니다. 꼭 기억해주세요.」

**3단계 · 확인** — `mode:"new"`일 때만 나타난다.
정규화된 사번과 이름을 크게 보여주고 「이 정보가 맞습니까?」를 묻는다.
`[다시 입력]` / `[네, 맞습니다]`. 오타로 인한 잠김 사고를 여기서 대부분 잡는다.

**4단계 · 선택** — 체크박스 두 개. 재로그인이면 이전 선택이 체크된 상태로 뜬다.
「둘 다 선택하지 않고 제출하시면 '이번엔 참여하지 않음'으로 기록됩니다.」

**5단계 · 완료** — 저장된 선택을 되짚어 보여주고,
「마음이 바뀌시면 같은 사번·이름·비밀번호로 다시 들어오셔서 고치시면 됩니다.」

모바일 반응형으로 만든다. 체크박스는 터치 대상이 충분히 크도록 행 전체를 클릭 영역으로 둔다.

### 6.2 관리자 (`admin.html`)

- 어디에서도 링크되지 않는다. 주소를 아는 사람만 연다
- 페이지를 열어도 **관리자 비밀번호 검증 전에는 어떤 데이터도 내려오지 않는다**
- 구성: 통계 요약 → ⚠️ 경고 목록 → 응답 테이블 → 대리 입력 폼
- 테이블 각 행: `[비번초기화]` `[수정]` `[삭제]`. 셋 다 확인 대화상자를 거친다
- `[표 복사]`로 탭 구분 텍스트를 클립보드에 담는다 (엑셀에 바로 붙여넣기)

### 6.3 노출 대응

GitHub Pages 사이트는 저장소를 비공개로 돌려도 **사이트 자체는 항상 공개**다.
소스만 숨겨질 뿐이며 이는 우회할 수 없다. 따라서 다음으로 대응한다.

- `<meta name="robots" content="noindex,nofollow">` — 검색엔진 색인 차단. 가장 중요.
  **`robots.txt`는 이 저장소에 두어도 실제로는 동작하지 않는다** — GitHub Pages
  프로젝트 사이트(`https://<계정>.github.io/<저장소>/`)에서 크롤러는 `robots.txt`를
  사용자 사이트 루트(`https://<계정>.github.io/robots.txt`)에서 찾지, 저장소 안에서
  찾지 않는다. 그래서 색인 차단은 전적으로 각 HTML의 `<meta>` 태그에 달려 있다.
  `robots.txt`는 해가 없고 사용자 사이트로 옮겨 배포하면 그때는 실제로 동작하므로
  남겨두되, 노출 대응책으로 세지 않는다
- 퇴직자 표기는 `김OO 책임님` 형태 — 사내 인원은 알아보지만 외부인에겐 의미 없는 문자열
- 응답 데이터는 비공개 구글시트에 있으므로 사이트에서 새지 않는다
- 외부인의 장난 제출은 관리자 화면에서 삭제한다

공용 참가 암호를 두는 방안은 검토했으나, 입력 단계가 늘어 응답률을 떨어뜨리는 비용이
얻는 것보다 크다고 판단해 채택하지 않았다. 필요해지면 로그인 화면에 칸 하나와
서버 검증 한 줄을 더하는 것으로 나중에 추가할 수 있다.

## 7. 통신 계층

### CORS 회피

Apps Script는 `OPTIONS` 요청에 응답할 수 없다. 따라서 **preflight를 유발하지 않는 요청만** 보낸다.

- `Content-Type: text/plain;charset=utf-8` (본문은 JSON 문자열)
- **커스텀 헤더를 하나도 붙이지 않는다** — 하나라도 붙으면 preflight가 발동한다
- 서버는 `e.postData.contents`를 `JSON.parse`한다

### 전송 방식 3단 대비

사내망 프록시의 거동은 실측 전엔 알 수 없다. `api.js`를 전송 방식이 교체 가능한 구조로 만들고,
1차 실패 시 2차로 **자동 전환**한다 (사용자에겐 보이지 않는다).

| | 방식 | 특징 |
|---|---|---|
| 1차 | `fetch` POST (text/plain) | 정상 경로. 응답 JSON을 읽는다 |
| 2차 | JSONP (`<script>` 태그 GET) | CORS 규칙 자체를 타지 않는다. 프록시가 CORS 헤더를 제거해도 동작 |
| 3차 | 화면을 Apps Script `HtmlService`로 이전 | 동일 출처가 되어 CORS 무관. **서버 로직과 시트 구조는 그대로 재사용** |

**JSONP의 대가**: 값이 URL 쿼리에 실려 프록시 접속기록에 비밀번호 4자리가 남을 수 있다.
1차가 되면 쓰지 않으며, 2차로 내려간 경우에만 감수한다. 3차는 코드 변경이 필요하므로
0단계 진단 결과를 보고 판단한다.

전환 판단은 **첫 요청 1회로 결정하고 그 결과를 세션 동안 유지한다.**
매 요청마다 1차를 재시도하면 실패할 때마다 지연이 쌓인다.

### 동시성

쓰기 작업(`save`, `admin*`)은 `LockService.getScriptLock()`으로 직렬화한다.
대기 30초, 초과 시 `BUSY`를 돌려주고 화면은 「잠시 후 다시 시도해주세요」를 띄운다.
108명이 동시에 몰릴 일은 없지만, 시트 읽기-수정-쓰기 사이에 다른 요청이 끼어들면
행이 덮어써진다. 안전장치는 필요하다.

## 8. 0단계 — 연결 진단

사내망에서 테스트할 기회는 귀하다. **회사 방문 한 번으로 모든 답이 나오도록** 진단 페이지를 먼저 만든다.

`test.html`이 검사하는 것:

1. `fetch` POST (text/plain) 왕복 성공 여부와 소요 시간. HTTP 200 만으로는 성공으로 치지
   않는다 — 사내 프록시가 차단 페이지를 200으로 돌려주는 일이 흔하므로, 본문이 JSON으로
   파싱되고 `ok:true`인지까지 확인한다 (`assets/api.js`가 실제로 요구하는 것과 같은 기준)
2. JSONP GET 왕복 성공 여부와 소요 시간
3. `script.googleusercontent.com` 도달 여부
4. 시트 읽기/쓰기 왕복 (진단 전용 `ping` 액션. `responses`를 건드리지 않는다)
5. `responses` 1행 헤더가 올바른지(`headerOk`). 시트는 만들었지만 헤더 행을 빼먹으면
   `sheetOk`는 그대로 true 라서, 이 검사가 없으면 첫 응답자의 제출이 헤더 자리에 실려
   조용히 사라지는 사고를 아무도 방문 전에는 알아채지 못한다

각 항목의 성공/실패와 **실패 시 에러 원문**을 화면에 표시하고,
`[결과 전체 복사]`로 진단 결과를 클립보드에 담는다.

### 진행 순서

1. 개인 gmail로 구글시트 생성, `responses` / `log` 시트 준비, A열 서식을 텍스트로 지정
2. 확장프로그램 → Apps Script → `Code.gs` 붙여넣기
3. Script Properties에 `ADMIN_PW_HASH` / `ADMIN_SALT` 설정 (편집기에서 1회 실행하는 셋업 함수 제공)
4. 배포 → 새 배포 → 웹앱 / 실행: **나** / 액세스: **모든 사용자** → `/exec` 주소 복사
5. GitHub 저장소 생성 후 Pages 활성화 (Settings → Pages → main)
6. `assets/config.js`에 `/exec` 주소 기입 후 push
7. **사내망 PC**에서 `.../test.html` 실행 → 결과 확인

7번 결과에 따라 전송 방식을 확정하고 나머지를 구현한다.
실패하더라도 **서버 로직·시트 구조·화면 마크업은 전부 재사용**되므로 버리는 작업은 없다.

## 9. 테스트 전략

빌드 도구 없이 브라우저와 Apps Script 편집기만으로 검증한다.

### 순수 함수 단위 테스트

정규화와 통계 계산을 부수효과 없는 순수 함수로 분리한다.

- 브라우저: `assets/normalize.js` → `tests.html`이 assertion을 실행하고 결과를 표로 출력
- 서버: `Code.gs`의 `normalizeEmpNo_` / `normalizeName_` / `computeStats_` →
  편집기에서 실행하는 `runTests_()`가 같은 케이스를 검증

**두 구현이 같은 케이스 표를 공유한다.** 정규화 규칙이 경계를 넘어 두 벌 존재하는 것이
이 구조의 유일한 중복이며, 동일한 테스트로 어긋남을 잡는다.

사번 케이스: `"1234"→"01234"`, `"01234"→"01234"`, `"1 2 3 4"→"01234"`,
`"1-234"→"01234"`, `"００１２３"→"00123"`, `"123456"→오류`, `""→오류`, `"abcde"→오류`

이름 케이스: `"홍 길동"→"홍길동"`, `"　홍길동　"→"홍길동"`, NFD 조합형 → NFC, `""→오류`

통계 케이스: 빈 목록, 전원 불참, `deleted` 행 제외 확인, 합계 정합성
(`both+onlyA+onlyB+none === total`, `a === both+onlyA`, `b === both+onlyB`)

### 시나리오 점검 (수동 체크리스트)

구현 후 실제 배포본에서 순서대로 확인한다.

1. 신규 가입 → 확인 화면 → 둘 다 체크 → 제출 → 시트에 행 생성
2. 같은 정보로 재로그인 → 이전 선택이 체크된 상태로 표시 → 하나 해제 → 시트 갱신, 행 수 불변
3. 앞의 0을 뺀 사번으로 로그인 → **같은 행**으로 진입 (중복 행이 생기지 않음)
4. 이름을 틀리게 입력 → `NAME_MISMATCH`
5. 비밀번호 5회 오입력 → 잠김 → 10분 경과 후 해제
6. 아무것도 체크하지 않고 제출 → 정상 저장, 통계의 `none`에 반영
7. 관리자 비밀번호 오입력 → 어떤 데이터도 내려오지 않음
8. 관리자 대리 입력 → 그 사람이 직접 로그인 → 비밀번호가 설정되며 진입 → 수정 가능
9. 관리자 비번 초기화 → 그 사람이 새 비밀번호로 진입
10. 관리자 삭제 → 통계에서 제외, 시트에는 `status='deleted'`로 잔존
11. 삭제된 사번으로 재가입 → 새 행이 아니라 기존 행이 되살아남
12. 브라우저 개발자도구로 `adminData`를 관리자 비밀번호 없이 호출 → `ADMIN_DENIED`
13. 참여자 API 응답에 `pwHash`/`salt`가 포함되지 않음을 네트워크 탭에서 확인

## 10. 보안 수준

명시적으로 밝혀둔다. **이것은 인사시스템급 보안이 아니다.**
자유 입력 방식이므로 사번을 아는 사람이 작정하면 남의 응답을 시도해볼 수 있다.
다만 다음으로 실질적 위험을 낮춘다.

- 비밀번호는 솔트 적용 SHA-256 해시로만 저장. 원문은 어디에도 남지 않는다
- 5회 실패 시 10분 잠금 → 4자리 숫자에 대한 무차별 대입 차단
- 관리자 비밀번호는 시트가 아닌 Script Properties에, 역시 해시로
- 참여자 API는 **자기 레코드만** 돌려준다. 남의 응답은 어떤 경로로도 조회되지 않는다
- 관리자 응답에서 해시와 솔트는 제외한다

담기는 정보는 사번·이름·불리언 두 개가 전부이며, 이 용도에는 이 수준이 적정하다.

### 행사 종료 후

구글시트와 Apps Script 프로젝트를 삭제하고, GitHub 저장소를 비공개로 전환하거나 삭제한다.
README에 이 절차를 적어둔다.
